# 合规单元 (ComplianceUnit) 理论体系详解

本文档旨在深入阐述 **合规单元 (ComplianceUnit)** 的理论体系。它是本合规自动化系统的核心基石，理解其构成、关系和处理流程，对于维护和扩展本系统至关重要。

本文所介绍的 **合规单元 (ComplianceUnit)** 是对旧版 **最小可执行单元 (MEU)** 的正式升级和替代。

---

## 1. 什么是合规单元 (What is a ComplianceUnit)?

**合规单元 (ComplianceUnit, 简称CU)** 是从金融法规中提炼出的、代表一项独立且可验证的合规要求的**原子单元**。它将一段非结构化的法规条文，转化为机器可以理解和执行的结构化对象。

每一个 `ComplianceUnit` 都由以下几个核心部分构成：

- **`cu_id`**: 独一无二的标识符，例如 `cu_04_1`，代表这是第4号法规的第1个合规单元。

- **`subject` (主体)**
  - **定义**: 规则所适用的**对象或实体**。它回答了“这条规则是关于谁的？”这个问题。
  - **作用**: 这是判断规则是否需要被考虑的第一道门槛。如果一家公司的行为或状态不满足`subject`的定义，那么与之相关的所有条件和约束都无需考虑。
  - **示例**: 自然语言 - "在股份回购期间的公司"。代码实现 - `df['是否在回购期间'] == True`。

- **`condition` (条件)**
  - **定义**: 规则生效所需的**特定情境或前提**。它回答了“在什么情况下这条规则才适用？”。
  - **作用**: 在满足`subject`的基础上，`condition`是第二道门槛。只有当特定条件也满足时，规则的约束力才真正生效。
  - **示例**: 自然语言 - "公司采用集中竞价交易方式进行回购"。代码实现 - `df['回购方式'] == '集中竞价'`。

- **`constraint` (约束)**
  - **定义**: 规则的**核心要求或禁令**。它回答了“主体在满足条件下必须做什么或不能做什么？”。
  - **作用**: 这是判断是否违规的最终依据。当`subject`和`condition`都为真时，如果`constraint`的结果为假，则构成一次**业务违规**。
  - **示例**: 自然语言 - "回购价格不得高于公司董事会通过回购决议前三十个交易日公司股票交易均价的150%"。代码实现 - `df['回购价格'] <= df['前30日均价'] * 1.5`。

- **`code` (执行代码)**
  - **定义**: 一段隔离运行的Python代码。
  - **作用**: 这是将理论变为现实的桥梁。这段代码接收公司数据（如交易记录、公告日期等），并负责计算出`_subject`, `_condition`, `_constraint`三者在每一条数据上的布尔值（`True`或`False`）。

- **`contextual_info` (上下文信息)**
  - **定义**: 对`code`中可能出现的硬编码值、阈值或“魔术数字”的自然语言解释。
  - **作用**: 提升规则代码的可读性和可维护性。它解释了为什么是这个数字而不是其他数字，使得规则的业务逻辑背景一目了然。
  - **示例**: 对于上面`constraint`中的`1.5`，`contextual_info`可以是 "根据法规原文，回购价格上限为前30日均价的150%".

## 2. 单元间关系 (Inter-Unit Relations)

法规的各个条款并非孤立存在，它们之间常常存在引用、排除、依赖等复杂关系。为了精确地模拟这种复杂性，我们引入了**关系 (Relation)** 的概念来定义CU之间的交互。

在合规图中，一个关系被定义为一条从`source`单元指向`target`单元的、带有类型的边。系统的 `RelationHandler` 模块负责在所有单元执行完毕后，根据这些关系来调整和修正初步的执行结果。

当前系统主要支持以下关系类型：

- **`refer_to` (参考)**
  - **简述**: 表示`source`单元在逻辑上参考了`target`单元（目标可以是其他条款、法规甚至公司章程）。
  - **逻辑细节**:
    - 这主要是一个信息性的链接，提示分析人员或未来的AI Agent，为了完整理解`source`单元，需要结合`target`的信息。
    - 它不直接参与违规计算的后处理逻辑。
  - **适用场景**:
    - "某某的认定参考某某法律文件"
    - "具体要求见附件4"
    - "后续处理应按照《公司法》办理"

- **`exclude` (排除)**
  - **简述**: 一个强逻辑关系。如果`source`单元的条件被满足（`subject`和`condition`均为`True`），那么`target`单元的所有规则将被忽略。
  - **逻辑细节**:
    - **作用时机**: 在所有CU独立执行得出初步结果后，计算最终违规状态之前。
    - `RelationHandler`会检查`exclude`关系，若`source`单元适用，则其`target`单元的最终状态会被标记为“被排除(Excluded)”，即使它本来是违规的。
  - **关键词**: "不受...限制", "免于遵守...", "除...以外"

- **`only_include` (仅包含)**
  - **简述**: 更强的排除关系。如果`source`单元的条件被满足，那么在某个范围内，只有`target`单元的规则会被考虑，所有其他单元都会被排除。
  - **逻辑细节**: 与`exclude`类似，它也在后处理阶段作用，但影响范围更广，会将其关系网络外的其他CU标记为“被排除”。

- **`should_include` (应包含)**
  - **简述**: 一个强制纳入的逻辑关系。如果`source`单元的条件被满足，那么`target`单元的核心约束(`constraint`)必须被遵守，即便`target`单元的适用条件(`condition`)在当前情境下不满足。
  - **逻辑细节**:
    - 这是为了处理法规中“在A情况下，也必须遵守B情况下的核心要求”这类复杂场景。
    - **作用时机**: 在后处理阶段。
    - **核心机制**: `RelationHandler` 在处理此关系时，会**强制`target`单元的`condition`为`True`**，然后重新计算其违规状态。这使得`target`单元的`constraint`检查被激活，从而可能揭示一个在常规流程下因`condition`不满足而被跳过的违规。
  - **关键词**: "应当符合/遵循本指引第X条的要求", "应当参照/按照...处理"
  - **重要区别**:
    - 与 `refer_to` 的区别: `should_include` 是强制性的，且指向本文内部条款；`refer_to` 是参考性的，通常指向外部文件。
    - 与 `only_include` 的区别: `should_include` 是“增加”一个必须遵守的项；`only_include` 是“排除”所有非必要的项。

## 3. 最终裁决：从执行到违规的后处理流程

得到最终的合规结论，不是简单地运行每个单元的代码，而是需要一个严谨的、包含关系处理的后处理流程。

流程如下：

1.  **独立执行 (Individual Execution)**
    - **前提**: 所有需要执行的CU的`code`都已在沙箱中针对公司数据运行完毕。
    - **产出**: 每个CU都对应一个结果DataFrame，其中包含为每一行数据计算出的 `_subject`、`_condition`、`_constraint` 的布尔列。

2.  **基础违规判定 (Basic Violation Assessment)**
    - 对于每个CU的结果DataFrame，系统进行第一次扫描。
    - **判定逻辑**: 如果某一行数据显示 `_subject=True`, `_condition=True`, `_constraint=False`，则该行被标记为一次**基础违规**。
    - **初步状态**: 如果一个CU包含至少一次基础违规，其初步状态被记为 "Violation"，否则为 "Success" 或 "Skipped"。

3.  **关系后处理 (Relation Post-processing)**
    - 这是决定最终结果的关键一步。`RelationHandler` 启动，并按预设顺序（如 `refer_to`, `should_include`, `exclude`...）处理所有关系。
    - **修正结果**: `RelationHandler`会根据关系的定义，修改在第2步中得到的初步状态。
      - 例如，一个初步状态为 "Violation" 的CU，如果它被另一个满足条件的CU通过`exclude`关系排除了，那么它的最终状态将不再是 "Violation"，而变为 "Skipped (Excluded)"。
      - 反之，一个初步为 "Success" 的CU，可能因为`should_include`关系被强制激活，从而暴露出违规，最终状态变为 "Violation"。

4.  **最终单元状态确定 (Final Unit Status)**
    - 经过关系后处理的所有修正后，每个CU都有了一个明确的最终状态（`Violation`, `Success`, `Skipped`, `Error`等）。

5.  **整体合规结论 (Overall Compliance Verdict)**
    - 系统最后汇总所有CU的最终状态。
    - **判定逻辑**: 只要有**任何一个**CU的最终状态是 `Violation`，那么本次对该公司的整体合规检查结论就是**不合规 (Non-Compliant)**。只有当所有CU的最终状态都不是 `Violation` 时，才能判定为**合规 (Compliant)**。
